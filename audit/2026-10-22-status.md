# EkDrive — where the project stands, 22 October 2026

Written for whoever picks this up next. It replaces [summary.md](./summary.md), which describes
a state the code left behind in September.

The September audit found an app whose routes did not call its own services. That is long
fixed. This note compares the code against the 22 documents in [`/plan`](../plan) and says what
is done, what is deliberately different, and what is still missing.

## Done since the last audit

**The data path works end to end and is tested against a real database.** Upload splits a file
into chunks, places them across drives by storage mode, verifies a checksum per chunk on the
way in and again on the way out, and a download reassembles them as a stream. Four chunks go up
at a time, an interrupted upload resumes, and a drive that refuses a write hands that chunk to
another drive with room.

**The pieces that surround it now exist too:** virtual folders (uploaded whole, downloaded back
as a zip), search, trash with a 30-day retention, public share links with their own management
screen, thumbnails for images, three storage modes with a rebalance, self-repair of missing
copies, drive health with uptime history, an activity log, notifications and an analytics
dashboard. The open page updates over a server-sent event stream rather than polling.

**Operationally:** scheduled jobs run with or without Redis, every Google call retries the
transient failures, each request logs one JSON line carrying a request id, and there are
container images and a compose stack.

**Security:** per-user rate limits across the whole API, an Origin check on cookie
authenticated writes, a locked-down CSP, `SameSite=Strict` sessions, and "sign out everywhere".

## Where the implementation deliberately differs from the plan

| Plan | What was built | Why |
|---|---|---|
| Serverless backend on Vercel with cron | One long-running Node process; jobs on timers, or BullMQ when Redis is configured | Uploads, downloads and zip streaming hold a connection for as long as Google takes. That fits a process, not a function with a request timeout |
| WebSocket with seven event types | Server-sent events, one stream per user | Every one of those events flows server→browser. SSE reconnects on its own and reuses the session cookie |
| Thumbnails in Redis, generated on upload | Generated on first request, stored in PostgreSQL | Generating at upload costs a full read back from Google for files nobody may ever list. The database already has to be there; Redis does not |
| `files.google_file_ids` / `drive_assignments` as the placement map | The `Chunk` table | One mapping, not two that can disagree. The columns were dropped |
| MinIO / object storage | Not used | `plan/architecture.md` ruled it out; chunks live on Google Drive |

## What is still missing

Ranked by how much it would matter next.

1. **Running more than one backend instance.** The rate limiter counts in memory, the rebalance
   lock lives in a `Set`, and without Redis the job scheduler is per-process. Each needs a
   shared store before a second instance can be started safely.
2. **End-to-end tests.** The integration suite drives the real HTTP app with Google mocked,
   which covers a great deal, but nothing exercises a browser. `plan/testing-strategy.md` asks
   for Playwright, and the five scenarios it lists are untested.
3. **The container stack has never been built.** Docker is not installed on the machine this
   was written on, so `docker compose up` is the thing that will prove or disprove it.
4. **No monitoring.** Logs are structured and have request ids, but there is no Sentry, no
   metrics endpoint and no alerting, so none of the thresholds in `plan/deployment.md` §9 can
   be measured.
5. **Accessibility is only as good as the work done by hand.** Dialogs trap focus, icon buttons
   are labelled, motion respects the system setting — but nothing has been run through axe and
   no screen reader has been near it.
6. **Frontend test coverage is thin** (~15%). The services and two components are covered; the
   pages are not.
7. **Smaller gaps:** drag-and-drop, toasts instead of inline notices, thumbnails for PDFs and
   video, Google Drive push notifications instead of polling for changes, per-drive API quota
   tracking, GDPR export and account deletion, key rotation for `ENCRYPTION_KEY`, and a
   per-folder storage-mode override.

Everything in [`plan/future-features.md`](../plan/future-features.md) — other storage providers,
version history, end-to-end encryption, mobile apps, the AI features — remains out of scope and
is not counted above.

## Taking it to production

The list above is what is missing from the plan. What it would take to put this in front of
real users — the Google consent screen, HTTPS, backups, monitoring, data rights — is a
separate checklist: [production-readiness.md](./production-readiness.md).

## How to check any of this yourself

```bash
pnpm typecheck && pnpm lint && pnpm test       # no database needed
pnpm --filter ekdrive-backend test:integration # needs DATABASE_URL; cleans up after itself
pnpm test:coverage                             # both suites, with the thresholds applied
```
